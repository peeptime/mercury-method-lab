# Skill 设计指南

> 版本：0.1.0
> 来源：Skill 最佳实践方法论（整合自 OpenClaw / Claude Code Skill 生态）

---

## 一、Skill 的本质

**Skill = 按需加载的经验固化工作流**

Skill 不是把提示词写长保存下来。它是把经验固化成一个：
- 可触发
- 可执行
- 可测试
- 可维护

的工作流。

---

## 二、三种上下文机制的区别

| 机制 | 加载方式 | 特点 |
|------|---------|------|
| **CLAUDE.md** | 常驻 | 只要在项目里就一直存在，持续影响行为 |
| **Slash command** | 手动触发 | 用户必须明确输入 `/cmd` |
| **Skill** | 按需匹配 | description 长期参与匹配，内容按需展开 |

Skill 的核心优势：**不需要用户记住叫它，Agent 自动识别场景后加载**。

---

## 三、description 是入口，不是说明书

description 写得好不好，直接决定 Skill 会不会被正确触发。

**反面例子：**
```
description: "Clean an input event into facts."
```
用户真实会说：
- "帮我把这个信息整理一下"
- "这些数据哪些是事实哪些是推测"
- "帮我分析一下这条信息"

**正面例子：**
```
description: |
  把输入事件拆成事实、推测、缺口和信源质量。
  触发词：整理信息、分析事实、区分推测、清洗材料、哪些是事实、来源是否可靠。
  不触发：要求生成内容、要求写文档、要求分析市场。
```

### 触发评估测试集（每个 Skill 必备）

写完 description 后，用真实用户表达测试：

```
✅ 应该触发：
  - [用户可能说的话A]
  - [用户可能说的话B]
  - [用户可能说的话C]

❌ 不应该触发：
  - [不该触发的话A]
  - [不该触发的话B]
```

---

## 四、渐进式披露（Progressive Disclosure）

**SKILL.md 是入口文件，不是所有资料的容器。**

SKILL.md 应该放：
- 什么时候触发
- 做事原则
- 执行步骤
- 需要哪些工具
- 验证方法

SKILL.md **不应该**放：
- 长篇参考文档
- 大量案例
- 详细模板（超过 200 行）
- 稳定可执行的脚本代码

### 分层结构

```
skill-name/
  SKILL.md              ← 入口，< 500 行
  references/           ← 长文档、风格参考、平台规范
    detailed-guide.md
  scripts/              ← 稳定可执行代码
    validate.sh
    export.py
  assets/               ← 模板、schema、示例
    template.md
    schema.json
```

这样做的好处：Agent 不需要每次加载所有内容。按需读取，按需执行。

## 五、工具边界（allowed_tools）

只给完成任务所需的最小权限。

```
整理资料 Skill：
  allowed_tools: [Read, Grep, Write]

分析审计 Skill：
  allowed_tools: [Read, Grep]

执行命令 Skill：
  allowed_tools: [Read, Write, Bash, Exec]

内容生成 Skill：
  allowed_tools: [Read, Write, Edit]
```

**核心原则：不要让只负责建议的 Skill 默认能修改文件。**

## 六、模型选择

不同任务适合不同模型：

| 任务 | 适合模型特点 |
|------|------------|
| 写文档、做总结 | 擅长写作和结构化输出 |
| 信息清洗、抽取 | 便宜快速即可 |
| 行动落地、方案翻译 | 需要推理和规划能力 |
| 审计、反方分析 | 需要批判性思维 |
| 生成内容 | 需要风格和表达控制 |

可以在 Skill 里指定：
```
model: "claude-sonnet-4"  # 或模型选择策略描述
```

---

## 七、disable 策略

使用频率低、专业性强、上下文成本高的 Skill，可以 disable 掉，降级为手动调用。

```
适合 disable：
- 年终总结（一年用一次）
- 简历重写（找工作阶段才用）
- 专题研究（按需触发）
- 低频专业分析

不适合 disable：
- 每次对话都可能用到的核心 Skill
- 高频工作流
- 入口级 Skill
```

## 八、Skill 验证闭环

### 第一层：能不能跑

```
- 文件路径对不对
- 工具权限够不够
- 脚本能不能执行
- 输出格式是否符合预期
```

### 第二层：能不能正确触发

准备触发测试集（见第三节），验证：
- 该触发的有没有触发
- 不该触发的有没有误触发

### 第三层：结果质量验证

准备 test data：
```
输入：[真实任务样本]
期望输出：[标准答案]
实际输出：[Skill 运行结果]
打分：0-10
```

评分标准：
- 0-2：完全没完成，方向错了
- 3-4：勉强相关，漏掉关键要求
- 5-6：基本可用，明显问题
- 7-8：质量稳定，少量细节可改
- 9-10：非常符合预期，可作示范

**最低标准：主要 test case 至少 5 分以上**

### 第四层：Baseline 对比

```
不用 Skill：X 分
用 Skill：Y 分
差值：Y - X = Skill 增益
```

如果 Skill 没有明显增益，说明它只是把常识固化了，没有带来额外价值。

### 第五层：迭代

| 失败类型 | 修法 |
|---------|------|
| 触发失败 | description 补关键词 |
| 误触发 | description 收窄边界 |
| 步骤漏掉 | 改 SKILL.md 步骤 |
| 输出格式不稳 | 加样例到 assets/ |
| 确定性检查不稳 | 写成 scripts/ |
| 工具权限不够 | 补 allowed_tools |
| 工具权限过大 | 收紧 allowed_tools |
| 模型能力不够 | 换更适合的模型 |

---

## 九、好 Skill 的检查清单

```
✅ 能被正确触发（description 包含真实用户表达）
✅ 不该触发时保持安静（边界清晰）
✅ 工具权限足够但不过度
✅ 模型选择符合任务成本和难度
✅ SKILL.md < 500 行，长内容分层到 references/
✅ 有触发评估测试集
✅ 有 test data 和打分标准
✅ 不只是写完了，还要能证明有效
```
