## 最关键的 6 个能力缺口（按 ROI 排序）

### 1. 真实用户回路 🔴 优先级最高
一个研究"如何审计 AI 输出"的项目自己 0/3 charter user，等于在没有水的池子里教游泳。
任何方法的优雅都需要被现实磨损一次才算数。

### 2. 测试 vs 文档严重失衡 🔴
100 倍以上的文档/测试比是危险信号。当前用"写得清楚"代替"跑得对"。

### 3. 缺少类型系统 🔴
以 schema/契约为核心的项目（packet、profile、standard、kernel result）不上类型，三个月后自己都会改不动。

### 4. 大文件未拆分 + 拒绝引入依赖 🟡
57KB 单文件 server 是 AI 一把梭出来的痕迹；不引入外部库等于拒绝学习别人已经踩过的坑。

### 5. 无 Pull Request 工作流 🟡
单人 force-push main 的习惯会把所有"被人 review"的肌肉记忆挡在门外。

### 6. Release theater 掩盖真实进度 🟡
9 天 14 个 release 的能量如果换成"找 5 个真人用 1 次"，价值会翻 10 倍。

## 外部建议：应该做什么（高 ROI）

### ① 少一层文档，多一例真实判例
每多写一个 governance doc 的边际收益，远低于多收集一份：
> "AI 在某真实场景里写了什么、被你怎么判了"

把精力从 doc 转向 case library（Proof Pack 001/002 是好的开始，但需要外部贡献的 case）。

### ② 挑一个真实下游死磕
把 mercury-audit 接到一个公开的 RAG 项目、Cursor 工作流、或 GitHub Copilot Chat 输出捕获里，让 method 见血。

### ③ 公开身份做内容
把 docs 改写成 3–5 篇高质量长文（中英双发），比再发 5 个 patch release 更能扩大影响力。继续匿名会让所有方法论可信度砍半。

### ④ 找 1–2 个工程方向上比自己强的合作者
把"工程毁灭性反馈"补回来。一个人在 main 上推 v1.9.0 的速度，越快越证明缺这一环。

### ⑤ 调试 AI 的工作方式
观察 Codex 在自己项目里的失败模式，写成可以复用的提示词与目录约定。这个能力今天还没有人做到大牛级别，对他来说是空位。
