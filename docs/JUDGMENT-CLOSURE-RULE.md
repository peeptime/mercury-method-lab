## 一、目标入口质量门（`/goal` 照妖镜）

在启动任何分析之前，目标必须通过 5 维度验证。

### 5 维度检查

| 维度 | 检查什么 | 典型失败信号 |
|------|---------|------------|
| **① 可交付物** | 有没有具体交付对象（文件/功能/报告/命令/API） | "更智能"、"优化一下"、"做好" |
| **② 可验证性** | 有没有验收标准或成功检查方式 | "做完就好"、"搞好" |
| **③ 时间边界** | 有没有明确截止日期 | "尽快"、"看情况"、"有空的话" |
| **④ 范围边界** | 有没有说明做到哪里算完 | "整个系统重构"、"所有流程" |
| **⑤ 责任归属** | 有没有说明谁来判断成功 | 缺责任人或验收方 |

**验证不通过** → 返回"照妖镜问题列表"，引导重写目标描述。
**验证通过** → 继续分析，同时运行四关检验。

### 四关检验（5维度全部通过后自动运行）

| 关卡 | 问题 | 通过信号 |
|------|------|---------|
| **案例关** | 它能解释哪个真实案例？ | 提及具体使用场景、真实用户、产品或项目 |
| **模板关** | 它能变成什么表格或流程？ | 提及模板、表格、流程、步骤清单 |
| **决策关** | 它能帮助谁做什么选择？ | 提及决策、判断标准、优先级、采纳/拒绝 |
| **反馈关** | 谁用了以后有结果？ | 提及验收、反馈、确认、报告、上线 |

四关用于判断概念的落地潜力，不是分析质量。

## 二、完整 PSP 判断关闭条件

每个完整 PSP 判断必须给出：

```text
【停止条件】满足什么条件后停止继续分析？
【推翻条件】什么信号出现说明当前判断错了？
【复盘时间】什么时候回来检查？
【记忆建议】M0-M4 记忆等级与理由
```

---

## 三、外部审计新增检查

审计报告除结构完整性外，必须检查：

- 证据是否独立（不依赖循环论证）
- 哪些是输入事实，哪些是模型推断
- 是否存在反例或缺失反例搜索
- 停止条件是否可执行（非模糊表达）
- 记忆等级是否偏高（M3/M4 需要外部证据支持）
- 目标是否通过 5 维度验证（如有对应 action_plan）

---

## 四、记忆等级

| 等级 | 含义 | 条件 |
|------|------|------|
| `M0` | 不建议记忆 | 推断为主，无外部验证 |
| `M1` | 可短期保留 | 逻辑自洽，待观察 |
| `M2` | 可作为项目上下文 | 经过一个真实案例验证 |
| `M3` | 可进入长期方法论 | 经过外部审计，无反例 |
| `M4` | 重大修正，高优先级保存 | 多个独立案例支持，经受住了反馈 |

**默认等级应偏保守。** 未经现实反馈的结论，通常不高于 `M2`。

## 五、Agent 模式下的执行要求

### 内嵌验证（零进程开销）

Agent 模式不得通过新建 Node.js 进程调用 `goal-validator.mjs`。

正确做法：在 Agent 上下文中直接内嵌 `validate(text)` 函数的判断逻辑：

```
用户输入
  ↓
Agent 自身执行 5 维度检查（内嵌逻辑，不新建进程）
  ↓
  ├─ 不合格 → 返回照妖镜问题（JSON 内嵌，不写盘）
  └─ 合格   → 继续分析，不额外读文件
              ↓
          通过四关检验
              ↓
          生成 action_plan artifact（含 Judgment Closure 字段）
              ↓
          写盘（仅此一步涉及文件系统）
              ↓
          npm run index + npm run validate
```

### 禁止事项

- ❌ 在分析过程中重新扫描项目目录补上下文
- ❌ 创建新进程执行 `goal-validator.mjs`
- ❌ 把未通过 5 维度的目标继续推进到分析阶段
- ❌ 跳过四关检验直接给出"方法论"级结论
