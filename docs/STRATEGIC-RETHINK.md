## 核心问题

Mercury Lab 到底应该优先成为：
- **完整系统**：仓库大、结构全
- **可被反复调用的判断质检单元**：小、硬、可验证

---

## 三个方向

| 方向 | 像什么 | 优点 | 隐患 |
|------|--------|------|------|
| A. 完整工作台 | 店长办公室 + 档案室 + 质检部 | 体系感强 | 越做越重，用户不知从哪开始 |
| B. 审计报告生成器 | 质检员写客诉调查报告 | 最容易理解、展示价值 | 退化成"更结构化的 AI 总结器" |
| C. Skill 孵化器 | 总部把经验压成员工 SOP 卡 | 最符合长期复用和 Agent 生态 | 需要强约束：触发/输入输出/失败样例 |

---

## 核心判断（待验证）

> **Mercury Lab 最该防的不是幻觉，而是"未验证判断被流程装修成成果"。**

这句话是中心假设，不是最终答案。需要被反例攻击。

## 四个核心讨论问题

### 1. 用户第一次使用时，最短路径应该得到什么？
决定产品入口。

### 2. 一个输出怎样才算"被 Mercury 改善过"？
决定验收标准。

### 3. 哪些内容永远不能被它自动确认？
决定安全边界。

### 4. 哪一种失败最不可接受？

| 失败类型 | 描述 |
|---------|------|
| 伪证据链 | 没有真实证据，但输出看起来像调查报告 |
| 伪审计 | 同一个模型自己生成、自己审计、自己通过 |
| 伪记忆 | 临时判断被写成长期原则 |
| 伪行动 | 生成了行动计划，但没有验收标准 |
| 伪闭环 | 目录、索引、报告都齐了，但没有外部反馈 |
| 过度保守 | 为了避免错误，导致系统无法产生可用结论 |
| 入口过重 | 体系完整，但陌生用户无法快速理解什么时候该用 |

## 当前 Mercurcury Lab 的禁止事项

已有明确禁止：
1. 不能把推测存成事实
2. 不能覆盖 raw 原始材料
3. 不能把所有东西写进长期记忆
4. 不能让同一个 agent 自己取证、判断、审计后直接定案
5. 不能清理掉未解释的异常信号

这说明项目核心不是"多做事"，而是**"少犯某些错误"**。

---

## 下一轮迭代的原则

> **不以"新增能力"为主题，以"定义不可接受的失败"为主题。**

不是缺想法，是需要让想法接受现实摩擦。

## 当前倾向

核心产物应该是 **Judgment Audit Report**，但要继续追问：

- 审计报告是**最终产品**，还是 skill/memory/decision 的**中间层**？
- 如果是中间层，下一步要打磨的是"从报告沉淀成 skill/记忆/决策"的**转换规则**
- 如果是最终产品，下一步要打磨的是报告质量：稳定、清楚、可复查
