# V2.0 · 审计忠实度与逻辑能力体系

> 问题来源：同分异构体审计案例实测反馈  
> 日期：2026-05-12  
> Provenance：`[HUMAN_ONLY]`

---

## 一、问题本质

本次实测暴露了 Mercury 当前版本的一个**系统性盲区类**：

> 审计报告的生成没有建立与原材料的**双向可追溯机制**。  
> 报告里的每一条结论、判断、问题，无法保证对应到原材料的具体位置。  
> 这导致了"报告写了材料没写"的结构性失真。

---

## 二、缺失的能力体系

### 能力族 1：报告忠实度验证（Report-Source Fidelity）

**问题描述：**  
审计报告的每个结论，必须能溯源到原材料的具体段落。报告生成器不能凭空生成"未解决的问题"，而应该先验证：该问题是否在原材料的后续内容中已被处理。

**当前缺失的表现：**
- 报告生成器按模板套用通用问题清单
- 不读取原材料的全部内容来验证问题是否仍存在
- "未解决"的判断是静态的，不追踪后续轮次

**需要的机制：**
```
输入：原材料（含多轮迭代的内容）
      +
      报告草稿（含"未解决问题"清单）

处理：
  对报告中的每个"未解决问题X"
  → 在原材料全文中搜索X的关键词
  → 检查X是否在原材料的后续段落中被处理
  → 如果已处理，标记为"已消解"，从报告的"未解决"列表中移除
  → 如果未处理，保留在报告的"未解决"列表

输出：带"消解状态"的审计报告
```

---

### 能力族 2：轮次感知与自我消解追踪（Iteration Awareness）

**问题描述：**  
对于多轮迭代型材料（如同分异构体审计），Mercury 需要识别"这是一个多轮消错过程"，并在审计时建立**轮次间的问题-解决对照表**。

**当前缺失的表现：**
- 把每一轮的内容当成同等地位的原材料
- 不追踪"第一轮提出的问题X"是否在第五轮被解决

**需要的机制：**
```
识别标记：第N轮 / 消错 / 审视 / 质疑 / 迭代 / iteration / audit round

处理：
  如果识别到多轮迭代结构：
  → 建立轮次间的"问题-解决追踪表"

  Example（同分异构体案例）：
  | 问题 | 提出轮次 | 状态 | 对应解决轮次及位置 |
  |-----|---------|------|-----------------|
  | "每一轮"绝对化 | 第一轮 | ✅ 已消解 | 第五轮：加了避免绝对化的补充说明 |
  | "重构"未定义 | 第一轮 | ✅ 已消解 | 第二轮：重新定义为"结构异构化+功能异构化" |
  | 外围干扰未剔除 | 第一轮 | ✅ 已消解 | 第三轮：明确剔除能源/制度/市场 |

  报告只输出：追踪表中"状态=未消解"的问题
```

---

### 能力族 3：元级审计识别（Meta-Audit Detection）

**问题描述：**  
Mercury 需要区分"原材料"（需要被审计的论断）和"审计过程本身"（已完成消错的元级材料）。

**当前缺失的表现：**
- 把已完成审计的材料，当成原材料来审
- 导致重复审计+错误的问题清单

**需要的机制：**
```
识别标记：
  - "第N轮"、"迭代N"、"消错"、"审视"、"审计过程"
  - 多段结构（第一轮/第二轮/第三轮...）
  - 元级语言（"这个论断的问题在于..."、"消解方式：..."）

处理：
  如果识别为"已完成审计的材料"：
  → 不执行常规审计（检查论断本身的来源/证据）
  → 改为执行"元级审计"：
      ① 审计这段审计过程本身的合理性
      ② 评估消错是否充分（参考能力族2）
      ③ 给出"这段审计的质量评级"
  → 输出格式从"routing_decision"变为"audit_quality_rating"
```

---

### 能力族 4：审计透明度与溯源标注（Audit Traceability）

**问题描述：**  
审计报告的每个结论，都应该有对应的溯源标注，让读者能验证报告的判断是否准确。

**当前缺失的表现：**
- 报告中的"问题A由材料第X段引发"等信息缺失
- 无法让读者或 review 人员快速核对原文

**需要的格式示例：**
```
## 审计结论

### 结论1：xxx
- 溯源：原材料第3段（"原论断..."）
- 评级：⚠️ 该问题已在第5段被消解
- 引用：[第5段] "避免绝对化描述..."

### 结论2：yyy
- 溯源：原材料第2段（"..."）
- 评级：🔴 未消解，需补充证据
```

## 三、能力体系的优先级

| 能力族 | 编号 | 优先级 | 理由 |
|--------|------|--------|------|
| 报告忠实度验证 | F1 | 🔴 P0 | 本次实测直接暴露的核心问题 |
| 轮次感知与消解追踪 | F2 | 🔴 P0 | F1 的实现依赖 F2 |
| 元级审计识别 | F3 | 🟡 P1 | 避免重复审计，有较高 ROI |
| 溯源标注 | F4 | 🟡 P1 | 提升报告可验证性，用户体验关键 |

## 五、实现建议

**不要在现有审计引擎上打补丁**（如 `auditKernel.mjs`），而是新增独立模块：

```
src/
├── mercury-audit/
│   ├── fidelity.mjs        ← F1：报告忠实度验证
│   ├── iteration-track.mjs ← F2：轮次感知与消解追踪
│   ├── meta-audit.mjs     ← F3：元级审计识别
│   └── trace.mjs          ← F4：溯源标注生成
│
├── audit-pipeline.mjs     ← 新增：统一编排上述四个模块
```

```
审计流程（修订后）：
  输入材料
    ↓
  元级审计识别（F3）
    ↓ 是否为已完成审计的材料？
    ├─ 是 → 进入元级审计路径
    │    ↓
    │    轮次感知（F2）→ 消解追踪
    │    ↓
    │    忠实度验证（F1）→ 生成带消解状态的报告
    │    ↓
    │    溯源标注（F4）→ 输出可验证报告
    │
    └─ 否 → 进入常规审计路径（现有逻辑）
         ↓
         忠实度验证（F1）→ 常规审计报告
         ↓
         溯源标注（F4）
```

## 六、F5 · 审计稳定性验证（v2.1.0 新增）

### 问题本质

Mercury 的路由决策（accept / revise / quarantine / discard）必须稳定：
同一份材料二次审计，不应给出截然不同的判断。
不稳定的结果本身就是一个质量信号——它说明审计过程受到随机因素干扰或存在 gaming 空间。

### F5 的四个检查维度

| 检查维度 | 内容 | 严重性 |
|---|---|---|
| routing_inconsistency | 两次运行 routing_decision 不一致 | 高 |
| low_fidelity_accept | fidelity_score 低但 routing 是 accept | 高 |
| confidence_routing_mismatch | confidence 标注与 routing 结果矛盾 | 中 |
| human_review_inconsistency | accept 无 human_review 但 fidelity 低 | 高 |

### 降级策略

```
accept  → revise  （不稳定时）
revise  → quarantine
quarantine → quarantine（不变）
discard → discard（终端状态，不降级）
```

### API 用法

```js
import { fullAudit, verifyAuditStability, applyStabilityGate } from "mercury-method-lab";

// 方式 A：在 fullAudit 中 opt-in
const result = fullAudit(content, { source_content: content, check_stability: true });

// 方式 B：显式调用
const result = fullAudit(content, { source_content: content });
const stability = verifyAuditStability(result);
const adjusted = applyStabilityGate(result, stability);
```

### F1-F5 × routing 联动

F1（低忠实度）和 F5（不稳定）有一个共同下游效应：

> 如果 fidelity_score < 0.8 或 stability_score < 0.8，
> routing_decision 应自动降级，且 human_review_required = true。

这不是"改变审计结果"，而是"让审计结果更诚实地反映不确定性"。

### 为什么 F5 比 F1 更难实现

F1 的验证对象是"报告 vs 原材料"——客观可查。
F5 的验证对象是"审计过程本身"——它要求运行两次并比较结果。

在 LLM 环境下，即使相同输入也可能产生不同输出的 token 概率分布。
F5 的实际意义不是"让两次结果完全相同"，而是检测"是否存在极端不一致（accept vs discard）"。
