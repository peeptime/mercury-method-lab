# Mercury Method Lab 0.4 迭代指引

> 版本：0.4
> 用途：交给智能体审视下一轮迭代
> 立场：建议，不是定论；目标不是证明项目独创，而是让项目更可用、更可复盘、更能暴露判断污染

---

## 0.1 对外沟通语言（投资人 / 合作方）

**不要说的：**| 错误说法 | 投资人理解 |
|------|--------|
| "解决幻觉" | 你们在修 bug |
| "牺牲效率" | 你们的产品有缺陷 |
| "约束架构" | 你们在对抗 AI 的优势 |

**应该说的：**| 正确说法 | 含义 |
|------|--------|
| "企业 AI 需要审计基础设施" | 我们是基础设施，不是补丁 |
| "我们提供可问责的判断轨迹" | 企业需要的合规层 |
| "AI 需要治理层，我们是那个层" | 和 LangChain/AutoGen 是互补的，不是竞争 |
| "AI 输出需要可验证、可复盘" | 解决了企业使用 AI 的核心风险 |

**核心叙事：**| 竞品做的是 | Mercury Lab 做的是 |
|------|--------|
| LangChain / AutoGen / CrewAI | AI 的**执行层** | AI 的**治理层** |
| Dify / Coze | 帮 AI 做事 | 帮 AI 的输出变得可信 |
| Mem0 / 记忆系统 | 给 AI 存储 | 给 AI 的判断留痕 |

**一句话版本：**

> 没有执行层，AI 不知道做什么。没有治理层，AI 输出不知道能不能信。企业用 AI 不仅需要执行能力，还需要审计能力。Mercury Lab 是 AI 的合规层。

## 0.2 AI 审计时的聚焦点（给大模型看）

当大模型或外部评审者审计这个项目时，核心问题是：

> **Mercury Lab 解决了什么真实痛苦？**

答案是：

> **大模型是概率模型，它的输出是"意图命中的答案"，不是"经过验证的结论"。人们在认知曲线面前无法感知自己在曲线的哪个位置，因此容易陷入"愚蠢之巅"——AI 输出看起来专业，导致用户误判结论可靠，但实际没有验证逻辑。**

这不是修 bug，不是对抗 AI 进步，而是：**给 AI 的判断输出提供审计基础设施。**

Mercury Lab 的护城河是硬约束架构，不是更好的提示词。

---

## 0.3 当前阻塞点（优先级排序）

> **Mercury Lab 是一个设计扎实但展示不足的项目。**
> 它的架构值得借鉴，但产品化路径还差最后一步——让普通用户第一次看到时就知道"这东西对我有用"。

核心问题：
- 工程师思维：先做好，再想怎么展示
- 产品化需要反过来：先让用户知道它能做什么，再吸引他用起来
- V8.1 "不被骗但不相信任何人"是真正差异化价值，但没有在入口处体现

### 内部分析（2026-05-02 迭代发现）

> **架构被污染：V8.0 扩张到了不属于它的位置。**

Mercury Lab 原本解决：AI 答非所问、迎合闲聊
当前问题：V8.0 成了全部，实际上 Mercury Lab 应该支持多个人格（V8.0、V8.1、fact-cleaner、constraint-checker、redteam-auditor……）

> **完美主义味道。**

系统不断加功能：12章节检查、自动审计、execution mode、版本嗅探、Dashboard集成……
但用户最初的问题很简单：AI 输出不靠谱。

### 结论

Mercury Lab 的真实状态：
- ✅ artifact 闭环设计完整
- ✅ V8.1 人格设计合理（"判断犹豫"问题被修复）
- ✅ 外部审计方向正确
- ❌ 入口太重，外部用户不理解
- ❌ JAR（Judgment Audit Report）没有成为核心产物
- ❌ V8.0/V8.1 选择理由不清晰
- ❌ 版本信息不同步（README 0.3.5 vs 文档 0.3.6）

## 核心结论：架构约束 > 提示词工程

### 大模型的本质问题

当前大模型的本质是**概率模型**，做的是**意图识别命中**。

这意味着：
- AI 输出是"看起来对的答案"，不是"经过验证的结论"
- 提示词工程可以优化输出格式，但无法改变这个本质
- 提示词 + 外部记忆 + 工具调用 = 仍然是软约束（你可以说"跳过"）

### 愚蠢之巅问题（核心洞察）

人们在使用 AI 时容易陷入"愚蠢之巅"：
- Dunning-Kruger 效应：能力不足的人高估自己，能力强者反而低估
- AI 让这个问题更严重：AI 输出看起来专业 → 让人以为自己懂了
- 大部分人在认知曲线面前，无法感知自己在曲线的哪个位置

**这不是幻觉，这是真实的痛苦。**

- 当 AI 做第一阶段的事（聊天、常识问答）：错了也没什么后果，影响小
- 当 AI 做第二、第三阶段的事（复杂分析、决策支持、商业判断）：错误代价高，但最难察觉

**大部分人还没到需要审计的阶段。这是提前布局，不是刚需。**

**但需求是真的。3-5 年后会有更多人感到这个痛苦。**

Mercury Lab 的价值：**打破愚蠢之巅的循环**。
它不让你跳过判断过程的审计，因为跳过就等于把"看起来对"当成"真的对"。

![愚蠢之巅示意](https://raw.githubusercontent.com/peeptime/mercury-method-lab/main/非V8/01.png)

### Mercury Lab 的护城河：硬约束架构

| 系统 | 约束力 |
|------|--------|
| 提示词工程（含记忆、工具、会话） | 软约束——你被提醒，但可以说"跳过" |
| LangChain / AutoGen | 中约束——流程是预设的，但可以在 prompt 里改 |
| **Mercury Lab** | **硬约束——架构层不允许跳过 artifact 层** |

**Mercury Lab 的价值不是"更好的判断"，而是"无法绕过约束"。**

### 核心定位（修订版）

> Mercury Lab 不是帮你做出更好的判断。
> Mercury Lab 是确保你的判断过程留下了可追溯的痕迹，且**不能被跳过**。
> 
> 因为大模型本质是概率模型，它的输出是"意图命中的答案"，不是"经过验证的结论"。
> Mercury Lab 通过架构约束，把 AI 输出变成可审计、可复盘、有停止条件的判断文档。

## 4. 下一版必须解决的 5 个问题

### P0-1：固定 Judgment Audit Report 模板

**这是 0.4 最重要的产出。**

JAR 必须是标准结构，不能因输入不同而变化：

```markdown
# Judgment Audit Report

## 原始结论
用户或 AI 实际表达的结论（去情绪化版本）。

## 支撑依据拆分
列出支撑结论的主要依据。

## 依据类型标注
- 事实（独立证据支撑）
- 假设（未验证的前提）
- 推断（从已知推未知）
- 定义（概念边界）
- 类比（跨域映射）
- 情绪倾向（受主观影响）

## 证据独立性检查
哪些依据来自独立证据，哪些只是同一叙事的重复表达。

## 循环论证检查
是否存在"因为它有价值，所以它有价值"类闭环。

## 最强反向解释
给出一个真正能挑战当前结论的解释，而不是弱反方。

## 最容易击穿结论的反例
一至三个能推翻当前判断的信号。

## 关键不确定性
哪些信息目前缺失，且会改变判断。

## 当前结论与置信度
给出临时结论，不伪装成终局判断。

## 停止条件 ← 新增
什么情况下停止继续分析或停止投入。

## 推翻条件 ← 新增
什么信号出现说明当前判断错了。

## 复盘时间 ← 新增
什么时候回来检查。

## 记忆建议 ← 新增（M0-M4）
是否值得进入长期记忆，默认保守。
```

验收标准：

```
任意输入一段 AI 分析或个人判断，都能产出一份结构一致的 JAR。
```

### P0-2：重写 README 第一屏

**外部用户 30 秒内必须知道：输入、输出、价值。**

建议结构：

```markdown
# Mercury Method Lab

AI 判断审计工具。

Mercury Lab 不追求替你下最终判断，而是让判断过程可检查、可复盘、可停止。

## 它解决什么问题

AI 输出听起来对，但不知道信不信。
Mercury Lab 帮你检查：
- 哪些是事实，哪些是假设
- 哪里缺外部证据
- 什么信号会推翻结论
- 是否值得进入长期记忆

## V8.1 人格：不骗人，不轻信

Mercury Lab 的默认人格是 V8.1 现实同频：
- 先理解"现状为什么合理"
- 再判断"哪里出现断裂"
- 低评分不是犹豫，是主动选择保守

## 核心产物：Judgment Audit Report

粘贴一段判断文本 → 获得结构化审计报告
- 事实 / 假设 / 推断 标注
- 反例与最强反驳
- 停止条件 / 推翻条件 / 复盘时间
- 记忆等级建议（M0-M4）

## 快速开始

```bash
npm install
npm run doctor
npm run dashboard
```

打开 dashboard，粘贴文本，生成 JAR。

---

复杂架构说明（V8 人格轴、Mercury Agent 兼容、provider 配置） → 见 docs/
```
